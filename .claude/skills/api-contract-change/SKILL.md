# Изменение API-контракта

У проекта живые платящие пользователи и внешние потребители `/api/*`.
Откат стоит дорого.

## Шаг 1. Пойми, меняешь ли ты контракт

**Это изменение контракта** (требует явного разрешения):

- новый или удалённый путь `/api/*`;
- изменение метода, кода статуса, формы тела ответа;
- переименование, удаление поля или смена его типа;
- изменение семантики поля при том же имени;
- изменение заголовков: `Cache-Control`, `ETag`, CORS, `Content-Type`;
- изменение правил пагинации, сортировки, значений по умолчанию;
- ужесточение валидации входа — раньше принимали, теперь 400.

**Это не изменение контракта:**

- добавление необязательного поля в ответ;
- рефакторинг без изменения наблюдаемого поведения;
- ускорение, кэширование с тем же результатом;
- правки логов и внутренних имён.

## Шаг 2. Если контракт не меняется

Тесты — источник истины. Они должны пройти **без правок**:

```bash
npm run test:<домен>-routes
npm run test:public-api
npm run test:routes
```

Пришлось поменять тест, чтобы позеленело, — значит ты всё-таки изменил
контракт. Откатывайся к шагу 1.

## Шаг 3. Если контракт меняется намеренно

1. Получи явное подтверждение — не решай сам.
2. Обнови contract-тест **в том же коммите**, что и код.
3. Обнови владеющий документ в `docs/specs/`: публичное поведение, API, данные
   и права живут там. Это заявленный `Documentation impact`, без него задача
   не считается завершённой.
4. Проверь потребителей: `src/`, `scripts/e2e-qa.mjs`, `tests/route-inventory`,
   `tests/seo-registry`, внешние клиенты из `docs/`.
5. Опиши изменение в `CHANGELOG.md`.
6. Для несовместимых изменений — версионируй путь, не ломай старый.
   Действующий контракт версионирования — ADR 003 (`docs/decisions/`).

## Шаг 4. Проверь целиком

```bash
npm run test:public-api && npm run test:route-inventory && npm run test:routes
npm run qa:e2e
```

## Чего не делать

- Не менять тест, чтобы он прошёл под новый код, если контракт не менялся
  намеренно.
- Не «чинить» падение contract-теста правкой ожидаемого значения.
- Не удалять поле, потому что оно «вроде не используется» — проверь
  потребителей.
- Не смешивать изменение контракта со структурным рефакторингом в одном
  коммите.
