# ADR-0002: единая платформа изображений колод для Arena и Telegram

> Архивное предложение от июля–августа 2026 года, сохранено при объединении
> веток. Это не описание текущего production и не утверждённый план внедрения.
> Домены, оценки, технологии и показатели ниже требуют повторной проверки.

- Статус: предложено
- Дата: 31 июля 2026 года
- Область: `arena.hs-manacost.ru`, Deckview Telegram bot и публичный render API

## Контекст

Arena и Telegram используют одну предметную область — код колоды, изображения карт и пользовательский дизайн, — но получают результат разными путями. Повторное разрешение колоды, ожидание очереди, повторная композиция и повторная загрузка одинакового файла в Telegram создают задержку, даже когда итоговые пиксели уже можно было подготовить заранее.

Текущая production-телеметрия Deckview на выборке из 827 завершённых запросов показывает:

| Участок | p50 | p95 |
| --- | ---: | ---: |
| Telegram целиком | 1 966 мс | 7 455 мс |
| Arena/web API целиком | 452 мс | 1 450 мс |
| Разрешение данных колоды при cache miss | 1 133 мс | 1 373 мс |
| Композиция Pillow при cache miss | 271 мс | 424 мс |
| Ожидание Telegram-очереди | 751 мс | 810 мс |
| Доставка в Telegram | 331 мс | 575 мс |
| JPEG-кодирование | 18 мс | 21 мс |

Следовательно, замена одной графической библиотеки не устранит основную задержку. Нужны общая идентичность артефакта, предрендер, точная инвалидация, обход очереди на cache hit и повторное использование Telegram `file_id`.

Сервер располагает AMD Ryzen 7 9700X, 8 физическими ядрами/16 потоками, AVX2/AVX-512 и 62 ГБ RAM. На момент решения CPU слабо загружен, поэтому для первого производственного варианта выгоднее использовать SIMD CPU-рендер и общий RAM-кэш, а не добавлять GPU.

## Решение

Создать отдельный долгоживущий сервис `manacost-renderd`, общий для Arena, Telegram и публичного API.

Сервис должен:

1. Принимать каноническую спецификацию колоды и эффективного дизайна.
2. Вычислять детерминированный `render_key` с учётом содержимого колоды, sideboard, ревизий карт, пользовательских файлов, версии шаблона, локали и выходного профиля.
3. Проверять общий content-addressed cache до разрешения внешних данных и до постановки задания в тяжёлую очередь.
4. Объединять конкурентные промахи по одному ключу через singleflight.
5. Один раз создавать master-артефакт и производные варианты для Arena и Telegram.
6. Хранить байты изображений в content-addressed filesystem/object storage, а не в BLOB-полях основной БД.
7. Хранить горячие соответствия и блокировки в Redis, долговечные метаданные и зависимости — в PostgreSQL.
8. Предрендерить изображения Arena при сохранении/импорте колоды и при изменении карты или дизайна.
9. Для Telegram хранить соответствие `(bot_id, artifact_hash) -> file_id` и повторно отправлять `file_id`, не загружая JPEG.

### Выбранный стек холодного рендера

- Rust + Axum/Tokio — процесс сервиса и API.
- Skia через `rust-skia` — композиция, текст, маски, градиенты, тени и blur.
- `fast_image_resize` — SIMD-ресайз карточных спрайтов в памяти.
- libvips — обработка больших пользовательских фонов и создание web-вариантов.
- libjpeg-turbo — Telegram JPEG.
- Redis — L1/L2 metadata cache, singleflight и Redis Streams для предрендера.
- PostgreSQL — долговечный каталог артефактов, зависимостей и Telegram `file_id`.
- Локальный NVMe/RAID filesystem CAS — горячие байты; object storage является необязательным холодным/резервным слоем.

### Идентичность артефакта

`render_key` является SHA-256 канонического документа:

```text
deck identity
+ ordered main cards, quantities and ownership
+ ordered sideboard groups and owners
+ per-card visual/layout/cost revision
+ effective design snapshot
+ SHA-256 of background/logo/curve replacement assets
+ renderer and template version
+ locale
+ output profile
```

API-ключ вызывающей стороны не входит в `render_key`, если он не меняет область доступа к приватным ресурсам. Артефакты неизменяемы: изменение любого входа создаёт новый ключ и новый URL; старый файл не перезаписывается.

## Альтернативы

### Оставить отдельные рендеры Arena и Telegram

- Плюсы: меньше начальных изменений.
- Минусы: двойная композиция, разные правила инвалидации, два кэша и расхождение дизайна.
- Решение: отклонено, потому что оба канала используют один канонический визуальный результат.

### Оптимизировать только Pillow

- Плюсы: минимальная миграция.
- Минусы: не устраняет разрешение данных, очередь, повторные загрузки и процессную фрагментацию RAM.
- Решение: Pillow остаётся временным fallback на период shadow-миграции, но не целевым движком.

### Node.js + Sharp/libvips как единственный движок

- Плюсы: Sharp уже используется Arena, простой вход для Node-команды.
- Минусы: Telegram всё равно потребует межпроцессный интерфейс; сложные эффекты и точный текст удобнее контролировать в отдельном render core.
- Решение: libvips остаётся частью конвейера производных изображений, но не владельцем всей композиции.

### SaaS-композиция Cloudinary/ImageKit/Cloudflare Workers

- Плюсы: CDN и управляемая эксплуатация.
- Минусы: 30–40 слоёв, длинные vendor-specific трансформации, квоты, cold latency и сложная воспроизводимость пользовательского дизайна.
- Решение: SaaS допустим для edge resize/format delivery готового master, но не как канонический compositor.

### GPU-рендер

- Плюсы: высокая пакетная пропускная способность при постоянно заполненной очереди.
- Минусы: копирование CPU↔GPU, отдельная эксплуатация, стоимость и отсутствие пользы на cache hit.
- Решение: отложено до измеренного насыщения CPU после внедрения CAS и предрендера.

## Последствия

- Arena и Telegram получают визуально идентичный результат одной версии.
- Cache hit не использует графический движок и не ждёт тяжёлую очередь.
- Страница Arena с сотнями колод не инициирует сотни холодных рендеров.
- Повторный Telegram-ответ ограничен в основном задержкой Bot API.
- Обновление карты инвалидирует только зависящие от неё колоды.
- Появляется отдельный критичный сервис, которому нужны health checks, метрики, резервирование metadata и контролируемый garbage collection.
- Rust toolchain на сервере необходимо обновить с текущего 1.63 до зафиксированной современной stable-версии в отдельном build-контейнере или toolchain directory.
- Диск уже заполнен примерно на 83%, поэтому production-включение CAS без quota и mark-and-sweep GC запрещено.

## Целевые SLO после миграции

| Сценарий | Цель p95 |
| --- | ---: |
| Локальный lookup готового артефакта | < 2 мс |
| Arena origin API для готового артефакта | < 10 мс |
| Холодный рендер стандартной колоды | < 120 мс |
| Холодный рендер XL/Reno | < 220 мс |
| Queue wait интерактивного запроса | < 20 мс |
| Доля cache hit после прогрева | > 95% |

Пользовательская задержка сети и Telegram Bot API не входит в SLO графического движка и измеряется отдельно.

## Проверка решения

- Golden-image тесты классического, пергаментного и пользовательского дизайна.
- Проверка sideboard, 30/35/40+ карт, русских/английских шрифтов, custom background/logo и blur.
- Сравнительный benchmark Pillow, Sharp/libvips и Rust/Skia на production-сервере.
- Нагрузочный тест cache hit, singleflight burst, холодной очереди и batch-prewarm.
- Shadow-режим с сохранением старого изображения до прохождения визуального допуска.
- Runbook отката на текущий Pillow renderer без изменения публичного API.

Подробный контракт и порядок реализации описаны в `docs/plans/unified-deck-render-platform.md`.
