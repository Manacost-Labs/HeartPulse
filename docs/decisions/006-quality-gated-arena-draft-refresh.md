# ADR-006: Атомарное обновление модели драфта по новым колодам

## Статус

Принято.

## Дата

2026-07-30.

## Контекст

Модель помощника драфта строится по потоку 12-победных колод
`hsreplay_arena_winning_decks`. Новые колоды появляются ежедневно, а патчи
меняют пул и мету. Ручной пересчёт оставляет модель устаревшей, но слепая
публикация каждого ответа источника может заменить рабочую версию неполной,
перекошенной или несовместимой выборкой.

Общая и классовые модели должны быть рассчитаны из одного снимка источников.
При ошибке должен оставаться доступен последний надёжный расчёт.

## Решение

Использовать один серверный refresh pipeline:

- запускать его ежечасно и после старта процесса;
- за один запуск загружать каждый внешний источник ровно один раз;
- принимать только полностью здоровую общую выборку;
- строить классовые модели при наличии минимум 20 забегов;
- отклонять пакет, если хотя бы одна публикуемая модель не проходит требования;
- записывать весь пакет одним атомарным обновлением истории;
- менять in-memory source cache только после успешной записи;
- объединять перекрывающиеся запуски внутри процесса;
- хранить ограниченный журнал запусков и безопасные метрики;
- сохранять закрытый admin API для статуса и ручного запуска.

Патч и fingerprint пула остаются границей когорты. Поэтому автоматический
контур не смешивает данные разных мет и не переносит взаимодействие карты,
вышедшей из пула.

## Рассмотренные альтернативы

### Обновлять модель при каждом пользовательском запросе

Плюс: всегда запрашиваются самые новые данные. Минусы: высокая задержка,
лишняя нагрузка на источник и риск того, что два администратора увидят разные
частично обновлённые классы. Отклонено.

### Публиковать классы независимо

Плюс: один проблемный класс не задерживает остальные. Минус: общая и классовые
модели могут относиться к разным снимкам и давать противоречивые советы.
Отклонено.

### Автоматически обучать веса рейтинга

Плюс: модель потенциально адаптируется глубже. Минус: поток содержит только
12-победные колоды, но не проигрышные забеги, полный набор предложений и
фактический выбор игрока. На таких данных нельзя надёжно измерить причинный
эффект изменения весов. Отложено до появления unbiased feedback dataset.

### Отдельный распределённый worker

Плюс: единый запуск при нескольких web-процессах. Минус: дополнительная
инфраструктура для текущего single-process production. Отложено; перед
горизонтальным масштабированием обязателен single worker или distributed lock.

## Последствия

- Новые колоды попадают в модель не позднее следующего часового запуска.
- Плохой внешний ответ не заменяет last-known-good.
- Все опубликованные классы относятся к одной когорте и снимку источников.
- После рестарта выполняется прогрев и фиксируется прерванный запуск.
- Оператор видит свежесть и результат без доступа к персональным данным.
- Система улучшает доказательность на новых наблюдениях, но не объявляет
  наблюдаемую связь причинным эффектом и не самонастраивает веса без контроля.
