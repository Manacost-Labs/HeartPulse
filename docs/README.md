# Каталог документации

У каждого документа есть один владелец и один тип. Не создавайте второй каталог
с тем же назначением и не копируйте одно правило в несколько мест.

## Основные разделы

- `docs/architecture/` описывает фактическую и целевую структуру приложения,
  границы модулей, направления зависимостей и измеримые migration ratchets.
- `docs/decisions/` — единственный каталог ADR. Здесь хранятся дорогие или
  труднообратимые решения, контекст, последствия и ссылки на заменившее решение.
  Исторический `docs/adr/` больше не используется; его документ перенесён сюда.
- `docs/specs/` фиксирует проверяемое продуктовое, API-, data-, permission- и
  UI-поведение. Спецификация меняется вместе с контрактом и тестами.
- `docs/operations/` описывает фактическое состояние развёрнутой топологии,
  владельцев и наблюдаемые ограничения. Это описание состояния, а не инструкция
  по внесению изменений.
- `docs/runbooks/` содержит пошаговые процедуры проверки, выкладки, диагностики,
  восстановления и отката. Опасные шаги обязаны иметь preflight и rollback.
- `docs/plans/` и `docs/roadmaps/` описывают незавершённую работу. Завершённое
  поведение переносится в architecture, specification, decision или runbook.
- `docs/design/` хранит визуальные правила и QA-контракты, а
  `docs/screenshots/` — их проверяемые изображения.

## Как выбрать место

- «Почему система устроена так?» — `docs/decisions/`.
- «Какой контракт должен сохраняться?» — `docs/specs/`.
- «Как сейчас устроен production?» — `docs/operations/`.
- «Что выполнить и как откатить?» — `docs/runbooks/`.
- «Какие зависимости разрешены?» — `docs/architecture/`.

Новый документ должен ссылаться на источник истины, а не пересказывать его.
Команды и пути проверяются в том же коммите; документация проходит
`npm run lint:docs`.
