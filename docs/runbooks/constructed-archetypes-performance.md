# Производительность каталога архетипов

## Контракт кеша

Первый этап плана от 19 октября 2026: уменьшить ожидание каталога при
обновлении источника, сохранив API, проверку подписки и публичный teaser.
Владелец — `server/modules/constructedArchetypes`; нормализация legacy-данных
пока передаётся из composition как зависимость загрузчика.

- Отдельный снимок для `standard` и `wild`; срок свежести задаёт существующий
  `DATASET_MEMORY_CACHE_MS` (по умолчанию 5 минут).
- После истечения свежести последняя успешная версия доступна ещё 15 минут,
  пока источник обновляется в фоне. Это соответствует существующему окну
  `stale-while-revalidate=900` публичного teaser. `updatedAt` не переписывается.
- На формат допускается одно одновременное обновление. Ошибка не продлевает
  срок допустимости сохранённых данных; повторное фоновое чтение — через 30 с.
- Без допустимого снимка запрос ждёт обновление не более 20 с и затем
  возвращает существующую ошибку API. После неудачного холодного запроса
  следующая попытка может повторить чтение.
- Неправильная структура источника и регрессия известного `updatedAt`
  не заменяют рабочий снимок. Корректный пустой массив допустим.
- Сброс parser-кеша инвалидирует также выполняющиеся обновления: запоздалый
  ответ не может вернуть очищенные данные в кеш.
- Кеш содержит общие данные источника. Авторизация и исключение платных полей
  остаются на существующих HTTP-границах; сессии и пользовательские ответы
  сюда не попадают.

## Срезы меты Стандарта

`/standard/meta/` (тизер, полный срез подписчика и смена фильтров) читает
срезы `формат:ранг:период:монета:минимум игр` из
`api.kolodahearthstone.com/v1/hsguru/meta`. Источник отвечает 1,4–3,3 с на
каждый срез и обновляет данные примерно раз в шесть часов; сброс parser-кеша
очищает срезы сразу. Раньше копия жила 5 минут, а затем запрос ждал источник:
каждые пять минут документ ждал весь бюджет первой отрисовки 600 мс и
приходил без тизера, а подписчик и каждое переключение ранга ждали 1,5–3 с.

- `createMetaSliceCache` из этого модуля: свежесть — тот же
  `DATASET_MEMORY_CACHE_MS`, затем 15 минут истёкший срез отдаётся сразу и
  одно чтение обновляет его в фоне. Одновременные чтения среза склеиваются.
- Ошибка или отклонённый кандидат (`selectStandardMetaCandidate`) оставляют
  последнюю проверенную версию бессрочно, как раньше; повтор — не раньше
  чем через 60 с. Конверт по-прежнему показывает настоящий возраст данных.
- После окна устаревания запрос снова ждёт источник (не более 20 с).
- После рестарта Express при `BACKGROUND_JOBS_ENABLED` прогревает срез, с
  которого открывается страница: период по умолчанию и текущий период.
- Числа, состав и порядок архетипов не меняются: кешируется тот же ответ.

Проверка: `npm run test:standard-meta-cache`; ручной замер — смена ранга у
подписчика и HTML `/standard/meta/` через 6–20 минут простоя среза.

## Приёмка и диагностика

Проверки на управляемом источнике: холодный запуск, двадцать конкурентных
запросов, граница TTL, зависший источник, сбой/восстановление, максимальный
возраст снимка, независимость форматов, сброс во время обновления и
некорректный ответ. Реальные таймауты моделируются на стенде; production-кеш
ради теста не очищается.

Сравнивать отдельно время HTML, доступности каталога и ответа API после
проверки подписки. Гостевой Lighthouse не измеряет готовность данных
подписчика. Не считать скорость localhost скоростью пользовательского
подключения. Поле `updatedAt` показывает время источника; возраст снимка
в памяти — отдельное ограничение и не делает данные источника свежее.

Исходный общий замер: мобильный LCP гостевого каталога 2,66 с, desktop 0,78 с.
Авторизованный production-сценарий пока не измерен; корректность доступа
проверяется изолированными API/browser fixtures без чтения чужих сессий.

## Проверки

- Кеш: `npm run test:archetypes-catalog-cache`.
- HTTP-контракт: `node --import=tsx tests/constructed-archetype-routes.test.ts`.
- Сброс parser-кеша: `node --import=tsx tests/parser-data-cache-invalidation.test.ts`.
- Компиляция сервера: `npm run build:server`.

Таймаут проверяется без реального ожидания через
[MockTimers Node.js](https://nodejs.org/docs/latest-v22.x/api/test.html#class-mocktimers).
Изменение включается обычным релизом сервера. Новых env-переменных, внешних
сервисов, фоновых расписаний или изменений БД не требуется. После рестарта
первое чтение остаётся холодным: постоянного дискового снимка здесь нет.

## Отдельные блоки и переходы

Сводка не ждёт `/api/auth/me` и `/api/subscription/status`; публичный seed и
две записи форматов на 30 секунд исключают повторные ожидания. Кеш форматов
живёт только в открытой странице, не содержит платных полей и не меняет
существующий App Router prefetch. Незавершённые запросы отменяются при уходе.

Сборки читаются через `section=core`; история и аналитика запрашиваются
параллельно отдельными блоками. Прежний полный API остаётся совместимым.
На стенде история и аналитика удерживаются десять секунд: сборка должна
появиться до их завершения и оставаться доступной при их ошибках. Повторная
попытка блока не должна перезапрашивать сборки. Проверка:
`npm run test:archetype-detail-loading` и
`node --test tests/next-archetypes-catalog-rendering-browser.test.mjs`.

Изменения карточек, библиотеки, LCP и CLS описаны в
[runbook производительности сайта](site-performance.md).

Core loading reserves a viewport before displaying optional placeholders;
otherwise a quick core reply pushes those visible placeholders off screen.
An explicit retry applies only to that read. Settled requests do not restart
when the public format cache updates or local search rerenders the page.
