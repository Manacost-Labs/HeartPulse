# Защита открытых JSON API от массовой выгрузки

Срез R8 эпика E21 (#367), задача #479. Код: `server/publicDataScrapeGuard.ts`,
классификатор путей `server/apiRateLimitPolicy.ts`, значения и режим
`config/public-data-api-guard.json`. Подключение: `server/index.ts`, сразу после
общего `apiLimiter`.

## Что защищено

GET и HEAD на `/api/**`, где есть сегмент `public`, `teaser` или `public-teaser`,
либо путь начинается с `/api/public/` или `/api/fun-decks`. Новые открытые
маршруты слоя попадают под правило сами. Админские маршруты и медиа
(`/api/public-resource/`, `/api/article-cover`) не затрагиваются. HTML-страницы
не затрагиваются: их получают все одинаково.

## Как работает

- Путь нормализуется как у Express: без учёта регистра, с декодированием,
  без двойных и хвостовых слэшей (`/api/Legendaries/PUBLIC` = тот же маршрут).
- Общий `apiLimiter` (120 в минуту) для открытых данных пропускает запрос
  только в режиме `enforce`: тогда единственный бюджет — этот guard, а
  подтверждённый бот и аккаунт не режутся общим лимитом. В режиме `log` общий
  лимит 120 в минуту остаётся защитным потолком (блокирует только его).
- Ключ клиента: IPv4 целиком, IPv6 по префиксу /64 (как в nginx-карте
  `$arena_public_profile_client`). Реальный IP берёт `getTrustedClientIp`
  (`trust proxy: loopback`), поэтому подделка `X-Forwarded-For` бюджет не
  обходит. Бюджет IP считается всегда; действующая сессия только поднимает
  потолок IP в `accountMultiplier` раз и добавляет бюджет самого аккаунта
  (общий для всех его IP). Несколько аккаунтов с одного IP бюджет не
  складывают.
- Два фиксированных окна: короткое (всплеск) и длинное (выкачка). Счётчики в
  памяти процесса, при рестарте сбрасываются; хранится не больше
  `maxTrackedClients` клиентов.
- Loopback (SSR Next, прогрев после деплоя) не считается.
- Превышение: `429`, JSON, `Retry-After` до конца сработавшего окна,
  `Cache-Control: no-store`. 403 и блокировки по User-Agent нет.
- Поисковые боты: если User-Agent заявляет Googlebot, Google-InspectionTool,
  YandexBot (или Bingbot) и клиент превысил бюджет, IP проверяется обратным DNS
  (имя в домене бота) и прямым DNS (имя даёт тот же IP). Подтверждённый бот лимита
  не имеет. Результат в LRU: подтверждение 24 ч, отказ 1 ч, сбой или таймаут DNS
  60 с. Таймаут DNS 1 с. Не подтверждённый «бот» лимитируется как обычный клиент.
- Лог: одна JSON-строка `public_data_scrape_guard` на клиента за окно
  (`limit_exceeded`) и при подтверждении бота (`bot_verified`). Без cookies,
  токенов и id из пути; IP в виде ключа клиента (IPv4 или префикс /64).

## Режим и откат

`"mode": "log"` пропускает всё и только пишет `limit_exceeded`;
`"mode": "enforce"` отдаёт 429. Файл читается при старте процесса: после правки
нужен перезапуск `hs-arena` (деплой). При нечитаемом файле действуют значения по
умолчанию в режиме `log`.

Откат при жалобах: коммит `"mode": "log"` и деплой; либо revert PR.

## Как поднять лимит

Правьте `shortMax` (запросов за `shortWindowSeconds`) и `longMax` (за
`longWindowSeconds`) в `config/public-data-api-guard.json`. Смотреть в логах:
`journalctl -u hs-arena | grep public_data_scrape_guard`, поле `client`,
`window`, `route`, `count`. Если превышают живые клиенты за мобильным CGNAT,
поднимайте `longMax`, а не отключайте guard.

## Значения по умолчанию

Короткое окно 60 запросов за 60 с, длинное 1500 за 3600 с, аккаунт ×3.
Обоснование: страница слоя в браузере делает 1-3 запроса к открытым JSON
(SSR ходит через loopback и не считается), сессия посетителя около 30-60 таких
запросов в час; запас ×10 на CGNAT даёт 600-1500 в час. Выкачка всей библиотеки
(тысячи сущностей) на 1500 в час растягивается на много часов и ловится по логу.
Это оценка по коду клиента, не по трафику: после релиза сверьте её с логом
режима `log`.
